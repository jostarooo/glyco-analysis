# AI 工程会话归档审阅指南

本指南说明老师应如何阅读本目录，以及这些材料能够证明什么、不能证明什么。

## 这份材料是什么

本目录是从本项目真实 Codex 会话中筛选并脱敏的工程记录。它不是重新编写的周报，也不是完整原始聊天的逐字导出。

每条工程判断都绑定以下证据之一：

- 用户消息的 `session_id + ordinal`
- 助手消息的 `session_id + ordinal`
- 工具事件的 `session_id + ordinal + call_index + event_index`
- 仓库中的命令输出、报告、测试结果或 Git 提交

证据原文的规范化 SHA256 记录在 [SOURCES.sha256](SOURCES.sha256)。

## 建议审阅路线

1. 先在 [INDEX.md](INDEX.md) 查看按日记录和会话清单。
2. 任选一天，阅读正文中的问题、决策、失败和验证。
3. 用正文里的证据 ID 对照该文件末尾的“证据索引”和“脱敏证据摘录”。
4. 检查证据摘录中的工具输出是否真的支持正文结论。
5. 最后阅读“判定边界”，确认哪些结论不能从当前证据推出。

## 证据强度

| 材料 | 能证明 | 不能证明 |
|---|---|---|
| 用户消息 | 当时提出了什么要求或约束 | 要求是否由学生独立提出 |
| 助手消息 | AI 当时给出了什么判断 | 该判断一定正确 |
| 工具命令和输出 | 当时实际执行了什么、返回了什么 | 当前环境仍能不加修改地复现 |
| 仓库报告与测试 | 当前提交中保存了什么结果 | 结果与上游论文完全等价 |
| 证据 SHA256 | 选定原文是否发生变化 | 模型回答是否真实或正确 |
| Git 提交 | 文件在某个时间进入了仓库历史 | 每一行代码由谁输入 |

## 建议优先核对的技术判断

### batch 64

`batch 256` 在 CUDA 上发生显存分配失败，随后用 `batch 64` 完成 2 个 epoch 的内存测试，再用于三种子、50 epoch 复算。证据见 `reports/w2_day1/glycanml_rgcn_recompute.json` 和 `reports/weekly/W02_2026-11-03_progress.md`。

### TLS 证书失败

`get_proteins` 默认证书校验失败不能直接写成服务死亡。诊断模式可以返回 HTTP 200 和 JSON，但不能因此关闭生产环境 TLS 校验。相关记录见 `2026-11-05`。

### HTTP 429

DeepSeek V4.1 免费路由出现 17 次 HTTP 429，导致大量任务没有工具调用。该运行只作为配额失败证据，不能作为模型能力结论。相关记录见 `2026-11-07`。

### F3 指标口径

`exact_sequence`、期望工具命中数、最终回答数量都是工具轨迹或输出存在性指标，不是答案正确率。Kimi K3 评分也只是本地证据评分，不等同于上游 GPT-4o。相关记录见 `2026-11-06` 和 `2026-11-07`。

## 如何验证归档没有被手改

```powershell
$env:PYTHONUTF8='1'
D:\python\python.exe scripts\build_agent_session_archive.py `
  --db D:\AppData\agentsview\sessions.db `
  --plan agent-sessions\archive-plan.json `
  --out agent-sessions --check
```

检查器会重新读取 AgentsView 中的选定证据，校验证据哈希、生成文件、脱敏结果和疑似密钥残留。手改正文、删除证据或注入高置信度 token 时应返回非零退出码。

## 明确不声称的内容

- 不声称本目录是完整逐字聊天记录。
- 不声称每段中文概述都由学生独立撰写。
- 不声称证据哈希可以证明技术结论正确。
- 不声称这份归档可以代替本人手写日志总结、现场讲解或周视频。
- 不声称 F2、F3 的本地结果与上游论文或 GPT-4o 评分完全等价。

如果老师要判断学生是否真正理解过程，仍需结合本人日志总结、现场演示和对关键失败案例的口头解释。

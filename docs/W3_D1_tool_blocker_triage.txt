一、今天解决什么问题

W2 的 50 题可行性分类使用了通用 wrapper 探测。通用探测能发现坏入口，却分不清
三种情况：

1. 探测参数本身不合法。
2. wrapper 或上游接口的契约有问题。
3. 服务真的不可达或持续返回 5xx。

这会把“模型没传对参数”误写成“服务失败”。本轮不重跑 F2 训练，不重跑 Qwen3 4B
的 50 题，只重测 W2 的 17 个阻断工具，并生成逐题修正证据。

二、复测口径

每个工具只使用可以从 W2 任务问题或 wrapper 文档还原出的参数。对于无法表达原任务
的入口，另加控制探针，确认服务能否接受同一数据域内的合法请求。复测只看工具是否
可达、HTTP 状态、返回内容是否符合预期，不评价模型回答正确率。

三类任务的最终口径：

- current_tools_direct：当前工具能用任务参数产出任务需要的结构或数据。
- needs_replacement_tool：工具可达，但接口、数据或任务表达仍需要一个替代入口，
  或者需要重构查询。
- service_failure：默认调用仍在传输层或服务层失败。

三、17 个阻断工具的复测结果

总计 17 个工具，服务可达 17 个，默认传输成功 16 个。

| 复测类别 | 数量 | 含义 |
|---|---:|---|
| passes_with_valid_args | 13 | 合法参数下可直接工作 |
| passes_but_task_needs_redesign | 1 | 单次工具可用，但原任务需要拆成多次查询 |
| api_contract_failure | 2 | 接口返回 200 或 400，但结果不满足任务契约 |
| tls_verification_failure | 1 | 默认证书校验失败，服务本身可达 |

需要拆查询的入口是 find。任务 28 同时要求 flavonoids 和 exact_mass=286.2，KEGG
的 find 接口一次只接受一种查询方式。合法 exact_mass 控制探针返回了 KEGG 行，所以
这不是服务死亡，而是任务需要两条查询或一个组合工具。

持续阻断的三个入口：

- get_lectins 使用 pdb 列时触发上游 SQL 错误：
  Column 'pdb' in field list is ambiguous。去掉 pdb 的 lectin 查询正常。
- convert_composition_text_to_wurcs_format 对任务 21 的复杂组成返回了 WURCS，
  但返回体写着 Accession not found，没有 GlyTouCan ID。标准组成控制探针能返回
  WURCS 和 G14669DU。
- get_proteins 默认调用的证书校验失败。verify=False 的诊断请求返回 HTTP 200 和
  可用 JSON，所以服务是活的，不能写成不可达。生产代码不能靠关闭 TLS 校验修复。

补充证据：

- generate_glycan_image 的 PNG 和 SVG 分支都返回 200，SVG 返回完整 svg 标记。
- convert_iupac_extended_to_wurcs 对任务 1 的完整输入返回 WURCS，但没有 accession；
  对任务 32 的截断输入返回 G22768VO 和 WURCS。任务 1 只要求 WURCS，因此两者都能
  继续后续步骤。
- get_ligands 返回 HTTP 200 和空数组。这是可达但没有可用数据，不是服务失败。

`TASKS` 映射；行数与划分计数均需核对。图解析沿用上游
`Glycan.from_iupac` 词表，活跃 unit 为 `127`，relation 为 `84`，embedding
行为 `143`。上游已为每个分支同时生成双向边，因此图中**不添加
`ToUndirected`、自环或边去重**。

## F2：模型与训练配置

| 项目 | 值 |
|---|---|
| embedding | `[143, 128]` |
| 消息传递 | 3 层；每层按 84 个关系分块计算逐关系均值，拼接关系通道后施加线性映射、自投影和 ReLU |
| pooling | 对三层拼接输出同时做 mean 与 max |
| 输出头 | `768 → 768 → num_classes` |
| optimizer | Adam，`lr=0.0005`，`weight_decay=0.001` |
| scheduler | `CosineAnnealingLR`，`T_max=100` |
| batch | 64 |
| epochs | 50 |
| seeds | `0, 1, 2` |
| device | `cuda:0`，RTX 5060 Laptop GPU，sm_120 |
| 选择规则 | 免疫原性按验证集 AUROC 选择检查点；糖基化按验证集准确率选择 |

说明：代码常量 `BATCH_SIZE = 256` 不是实际运行值，产物记录为
`training.batch_size=64`。batch 64 的两轮内存测试通过；batch 256 触发 CUDA
分配 OOM，因此完整运行使用 64。`torchdrug_installed=false`，没有进行
TorchDrug 数值逐位对照。本实现与 TorchDrug 结构相关，但不是克隆。上游
`link_RGCN.yaml` 把 `num_class` 写成 2，而 CSV 有三类；复算遵循 CSV。

## F2：论文目标与实测结果

| 任务 | 论文目标（Table 3 RGCN 行） | 实测 | 解释 |
|---|---|---|---|
| 免疫原性 | AUPRC `0.780 ± 0.006` | **`0.7748635136784087 ± 0.009111853148723878`** | 论文均值位于一个实测标准差内；不声称完整复现 |
| 糖基化 | Macro-F1 `0.948 ± 0.004` | **`0.9377928560029268 ± 0.0038891301525018625`** | 低于论文约 `0.010`；不声称完整复现 |

其他指标：

- 免疫原性测试 AUROC：
  `0.9730666666666666 ± 0.0012858201014657124`；测试准确率：
  `0.9241379310344827 ± 0.006896551724137945`。
- 糖基化测试准确率：
  `0.9613821138211381 ± 0.003520428470668453`。
- 逐种子测试 AUPRC：
  `0.7832559324152325 / 0.7651717289430979 / 0.7761628796768958`。
- 逐种子测试 Macro-F1：
  `0.9407962109575013 / 0.9333997727074045 / 0.9391825843438747`。

差异来自实现和训练细节，不能简化为“差 0.01 就是失败”。自实现关系层使用
分块逐关系均值，本地没有运行 TorchDrug 的关系卷积；模型与上游相关，但不能
直接加载上游检查点。后续消融可以比较图与序列，但当前绝对差距还不是模型
能力结论。

## F3：Doc2Agent 工具与任务盘点

对 70 个上游 wrapper 做直接导入和最小样例调用：

| 类别 | 数量 | 含义 |
|---|---:|---|
| `ok` | 43 | 直接调用成功 |
| `bad_request` | 12 | HTTP 400 或 422 |
| `param_error` | 6 | HTTP 前的 Python assert 或参数错误 |
| `api_error` | 2 | HTTP 2xx，但 payload 含错误字段 |
| `not_found` | 2 | HTTP 404 |
| `wrapper_bug` | 2 | HTTP 前的 Python 异常 |
| `http_424` | 1 | HTTP 424；服务可达但功能失败 |
| `server_error` | 1 | HTTP 5xx |
| `unreachable` | 1 | SSL 错误 |

`service_alive_rate=0.8714` 表示服务有响应，不表示调用成功。更严格的
`directly_ok=43/70` 才是直接成功率。`not_exercised=8` 汇总
`param_error + wrapper_bug + dependency_missing`；本轮没有
`dependency_missing`。

把 50 道题的预期轨迹与 wrapper 状态连接：

| 项目 | 结果 |
|---|---:|
| 总任务数 | 50 |
| 1 步、2 步、3 步任务 | `30 / 17 / 3` |
| 所有 wrapper 均为 ok | 20 |
| 至少一个 wrapper 非 ok | 30 |
| 上游 Claude 基线 | 18/50，GPT-4o 评分 |
| 上游 Qwen3 基线 | 15/50，GPT-4o 评分 |

`all_wrappers_ok=20` 是 wrapper 可行性的上限，不是模型成功率。三个 3 步任务
都包含非 ok wrapper，因此严格预期轨迹无法在当前 wrapper 集合上完成。应先
修复或绕过 HTTP 前的 wrapper，再决定 agent 是否需要替代工具。

## F3：Qwen3 试点为何不可比

| 模型 | 任务数 | 结果 | 解释 |
|---|---:|---|---|
| Qwen3 8B | 1 | Ollama HTTP 500 | 没有返回可用动作；工具调用为零 |
| Qwen3 4B | 1 | HTTP 500；llama-server 退出码 `0xc0000409` | 栈缓冲区溢出；没有返回可用动作 |

这些零只能证明本地运行时失败，不能证明模型不会选择工具，也不能写成
“能力为零”。上游 Claude 18/50 和 Qwen3 15/50 基线使用 GPT-4o 评分；本地
脚本统计工具轨迹和调用状态，没有运行该评分器，因此**这些数字不可直接
比较**。`qwen3:0.6b` 下载也没有完成，没有启动 50 题运行。
